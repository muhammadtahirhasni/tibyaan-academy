### 8d. Why did the daily dars stop after 14 May?

**I could not determine this conclusively, and I want to be straight about that.** There is no
`.env.local` in the repo and no database access from this machine, so I could not read
`agent_logs` (which records every agent run with `status: 'error'` and the error message) or the
`daily_dars` rows. Those two tables will answer the question directly.

What the code and git history *do* establish:

1. **`vercel.json` declares 5 cron jobs. Vercel's Hobby plan allows 2.** Commit `b337ba9`
   (2026-03-29) is literally titled *"fix: change dars-circles reminders to daily cron (Vercel
   Hobby limit)"*, which confirms the project was on Hobby. On Hobby, crons beyond the limit are
   not registered, and daily crons fire at an approximate time rather than the stated one. This
   is the single most likely cause.
2. **A 401 is silent.** `/api/dars/generate` returns 401 unless the `Authorization` header
   matches `CRON_SECRET`. If `CRON_SECRET` was rotated, cleared, or never set on the production
   project, every invocation fails with no alert anywhere.
3. **Failures die silently by design.** `BaseAgent.execute` catches everything, writes an
   `agent_logs` row, and returns `status: 'error'`; the route returns 500. Vercel Cron does not
   retry, and nothing emails or messages you. A job could have been failing daily since 14 May
   with no visible signal.
4. The last deploy touching `vercel.json` was `0d1e046` on **2026-05-08**, six days before the
   last dars. Consistent with a deploy-time change to cron registration, but not proof.

**To settle it, check in this order:**
1. Vercel → project → Cron Jobs: is `/api/dars/generate` listed and enabled? What are its last
   run timestamps and status codes?
2. `SELECT agent_name, status, error, created_at FROM agent_logs WHERE task_type = 'generate_daily_dars' ORDER BY created_at DESC LIMIT 20;`
3. `SELECT slug, created_at, status FROM daily_dars ORDER BY created_at DESC LIMIT 10;`
4. Vercel → Settings → Environment Variables: is `CRON_SECRET` set on Production?

## 9. Plan: ground generated content in the uploaded books

**Plan only — no code written.** Goal: the generator stops citing from model memory and can only
cite passages that actually exist in your PDFs, or produces nothing.

### 9.1 Two separate stores, deliberately

| | **Kitab store** (this plan) | **SEO/marketing store** (existing behaviour) |
|---|---|---|
| Source | Your uploaded syllabus + reference PDFs | Keyword lists, country pages, brand copy |
| Purpose | Religious accuracy — Quran, hadith, fiqh, seerah | Ranking and traffic |
| Rule | Abstain if not found | Free generation, no citation requirement |
| Tables | `kitab_documents`, `kitab_passages` | unchanged |

They never share a table and never share a retrieval call. A marketing paragraph must not be able
to reach into the kitab store and borrow authority from it, and a hadith must never be sourced
from a keyword doc. This is the whole reason for the split.

### 9.2 Ingestion — PDFs to passages

New tables in the existing Neon database (pgvector is available on Neon via
`CREATE EXTENSION vector`):

```
kitab_documents
  id, title, author, edition, language, source_path (R2 key),
  total_pages, sha256, ingested_at, is_active

kitab_passages
  id, document_id → kitab_documents,
  page_from, page_to, chapter, section,
  content       text        -- the passage as it appears
  content_norm  text        -- diacritics stripped, for lexical search
  token_count   int
  embedding     vector(1024)
  created_at
  -- indexes: HNSW on embedding; GIN on to_tsvector(content_norm)
```

**Chunking:** ~500–800 tokens with ~100 token overlap, split on structural boundaries
(chapter → section → paragraph) rather than a fixed character count, so a hadith and its
attribution never land in different chunks. Every chunk keeps its page range — that is what makes
a citation checkable.

**Extraction:** the PDFs are Arabic/Urdu, so plain `pdf-parse` will not be enough for scanned
pages. Budget for OCR (Google Document AI or Azure Document Intelligence, both good at Arabic
script) on any document whose text layer is empty. Ingestion is a one-off offline script, not a
request-path job.

**Embeddings:** a multilingual model is required — Arabic, Urdu and English queries must hit the
same space. Voyage `voyage-3` (multilingual, 1024-dim) or Cohere `embed-multilingual-v3`.
OpenAI's `text-embedding-3` is weaker on Arabic.

### 9.3 Retrieval and forced citation

Per generation run:

1. Build a query from the topic/category.
2. **Hybrid retrieval**: vector similarity (top 40) ∪ BM25/`tsvector` lexical (top 40) — lexical
   matters because an exact hadith number or name is a keyword match, not a semantic one.
3. **Rerank** to top 8 with a cross-encoder (Cohere Rerank, or Claude scoring each passage).
4. Pass those 8 to Claude as numbered blocks, each tagged `[P1] … [P8]` with document title and
   page range.
5. Require the model to return structured output where **every factual claim carries the passage
   id it came from**:

```json
{
  "title": "...",
  "body_html": "...",
  "claims": [
    { "text": "The Prophet ﷺ said …", "passage_id": "P3" }
  ],
  "citations": [
    { "passage_id": "P3", "document": "Sahih Bukhari", "pages": "412-413", "quote": "…" }
  ],
  "abstained": false
}
```

6. **Post-generation verification, in code, not in the prompt**: for each citation, confirm the
   `passage_id` was actually in the retrieved set, and that `quote` appears verbatim (after
   normalisation) in that passage's `content`. Any citation failing this check → reject the whole
   draft. This is the step that catches a confidently invented hadith number, because the model
   cannot fabricate a quote that is present in a passage it was handed.

7. Store the passage ids on the draft so the review page can render **"Citation: Sahih Bukhari,
   pp. 412–413"** as a link to the exact passage text (and the source PDF page). The reviewer
   verifies against the book, not against the model's say-so. This slots directly into the
   citation panel already built in `/admin/content-review`.

### 9.4 Abstention

Two hard gates, both in code:

- **Retrieval gate**: if the best reranked passage scores below a calibrated threshold, stop.
  Do not call the generator at all.
- **Output gate**: the model is instructed to return `{"abstained": true, "reason": "..."}` when
  the passages do not support the topic, and any draft failing quote-verification is discarded.

An abstention writes a row with `status = 'draft'` and the reason, so you can see *"asked for a
hadith on X, nothing in the corpus covers it"* — that is a useful signal about gaps in the
uploaded books, not a failure. Critically: **abstention produces nothing publishable.** It never
falls back to unsourced generation.

### 9.5 Effort and cost

| Piece | Effort |
|---|---|
| Schema + pgvector migration | 0.5 day |
| PDF extraction + OCR fallback + chunker | 2–3 days (OCR quality on Arabic is the variable) |
| Embedding + ingestion script, re-runnable | 1 day |
| Hybrid retrieval + rerank | 1.5 days |
| Generator rewrite with structured citations | 1.5 days |
| Quote-verification + abstention gates | 1 day |
| Review-page citation links | 0.5 day |
| **Total** | **8–10 working days** |

**Running cost (rough, order-of-magnitude):**

- *One-off ingestion*: OCR ≈ $1.50 per 1,000 pages; embeddings ≈ $0.02 per 1M tokens ingested.
  For 5,000 pages ≈ **$10–20 total**, repeated only when books are added.
- *Per generated post*: 1 embedding call (negligible) + 1 rerank (~$0.001) + 1 Claude call with
  ~6k tokens of passages in and ~2k out. On Sonnet that is roughly **$0.05–0.08 per post**,
  versus ~$0.02 today — call it **3× the current per-post cost**, on a base that is already
  cents.
- *Storage*: 5,000 pages ≈ 10k passages ≈ 40 MB of vectors. Inside Neon's existing footprint.

The cost is not the constraint. OCR quality on Arabic and Urdu scans is the real risk, and it is
worth ingesting one book end-to-end and eyeballing the passages before committing to the rest.
